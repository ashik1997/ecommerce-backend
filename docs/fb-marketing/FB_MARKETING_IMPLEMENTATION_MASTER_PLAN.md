# FB MARKETING — Master Implementation Plan

Prepared for the uploaded Laravel ERP project.

## Purpose

Build a tenant-safe **FB MARKETING** control center inside the ERP. A permitted user must be able to configure Meta credentials from the dashboard, sync Meta assets, inspect and control campaigns, measure advertising cost against ecommerce sales and profit, generate reports, review audit logs, and read an embedded user manual without editing application code or Meta-specific `.env` values.

This file is the planning baseline. At implementation start, add a compact `FB_MARKETING_STAGE_TRACKER.md` to the project root and store detailed stage notes under `docs/fb-marketing/stages/`.

---

## R&D baseline from the uploaded project

### Existing foundations to reuse

- Laravel `8.75`, PHP `^7.3|^8.0`.
- Global `TenantDbMiddleware` switches the tenant database by domain.
- Sidebar configuration is generated by `app/Http/Helpers/BackendSidebarHelper.php` and filtered through role sidebar permissions.
- CRM already demonstrates staged delivery, audit history, approval boundaries, immutable snapshots, permission keys, and tenant-aware code patterns.
- Existing ecommerce and ERP reporting foundations include `product_orders`, `product_order_products`, product allocations, `net_profit`, `contribution_profit`, returns, refunds, courier settlement, and analytics actions.
- Existing PDF and spreadsheet dependencies are available through `barryvdh/laravel-dompdf` and `maatwebsite/excel`.
- Database queue migrations exist, although the default queue is currently `sync`.
- Laravel scheduler infrastructure exists in `app/Console/Kernel.php`.

### Existing Facebook-related foundations to consolidate

- Facebook pixel-related fields currently exist in `general_infos`.
- A public XML feed endpoint exists at `/api/facebook-product-feed.xml`.
- Products already expose a Facebook feed checkbox.
- The feed implementation currently checks `is_facebook_feed`, while the product form uses `is_facebook_product_feed`. This mismatch must be repaired before catalog reporting is trusted.
- Existing backend project files do not contain a complete Marketing API module, campaign sync layer, attribution ledger, CAPI event ledger, or Graph client.

### Security issues that must be closed before saving Meta credentials

- Remove public or unsafe maintenance/debug routes from production exposure, including direct login/test, destructive seeder, public migration, append-column, dump, and phpinfo-style exposure.
- Move any unrelated hardcoded provider secrets out of source control.
- Add secret-redaction rules so tokens and app secrets never enter logs, exception output, browser payloads, or exports.

## Non-negotiable architecture decisions

### 1. One implementation stage per chat

Each chat implements exactly one FBM stage. A blocker repair may be included only when required for that stage and must be documented.

### 2. Compact tracker plus separate stage notes

Avoid a single oversized tracker.

```text
FB_MARKETING_STAGE_TRACKER.md                 # compact status index and next command

docs/fb-marketing/ARCHITECTURE.md            # stable architecture decisions

docs/fb-marketing/DB_MAP.md                  # evolving database map

docs/fb-marketing/API_MATRIX.md              # Meta endpoints, scopes, fields and sync rules

docs/fb-marketing/REPORTING_DEFINITIONS.md    # metric definitions and attribution rules

docs/fb-marketing/stages/STAGE_XX_*.md        # detailed notes for each implemented stage
```

A later chat should read the compact root tracker first and open only the necessary stage note.

### 3. Meta credential values are database-managed

No Meta credential is read from `.env`.

Store per-tenant Meta configuration in encrypted database columns. Users with the correct permission can add, rotate, test, disable, and replace credentials from the UI.

The Laravel `APP_KEY` remains a server-side application invariant because it protects encrypted database values. It is not a Meta credential and must never be stored beside encrypted secrets in the same database.

### 4. Read-only before write operations

Implement asset discovery, sync, snapshots, reports, audit logging, and preflight validation before enabling campaign publishing or budget changes.

### 5. Reporting must distinguish attribution meanings

Never label all sales during a campaign as confirmed Facebook sales.

Use separate metrics:

```text
Meta Reported Revenue
ERP Attributed Sales
Campaign Window Sales
Comparable-period Sales Uplift
```

### 6. Writes use approval, audit, idempotency, and preflight checks

Campaign publishing and budget changes must not be direct untracked form submissions. Every write action records actor, before-state, after-state, request fingerprint, response reference, outcome, and timestamps.

## Reporting definitions

```text
ROAS = ERP Attributed Sales / Meta Ad Spend

Meta ROAS = Meta Reported Revenue / Meta Ad Spend

Campaign-window ROAS = Campaign Window Sales / Meta Ad Spend

Ad-adjusted Contribution Profit = ERP Contribution Profit - Meta Ad Spend - Local Campaign Cost Adjustments

Cost per ERP Attributed Order = Meta Ad Spend / ERP Attributed Order Count

Sales Uplift = Campaign Window Sales - Comparable Previous Window Sales
```

When product-level spend is not directly returned for a campaign type, the report must mark allocated spend as an estimate and store the allocation rule used.

## Per-chat implementation protocol

At the start of each implementation chat:

```text
1. Upload the latest full project ZIP.
2. State the exact stage command only.
3. Inspect FB_MARKETING_STAGE_TRACKER.md first.
4. Verify the previous completion gate.
5. Implement only the requested stage.
6. Run targeted validation.
7. Update the compact tracker and create one detailed stage note.
8. Return a new full-project ZIP and the next exact command.
```

Minimum validation after every stage:

```text
PHP syntax lint for changed PHP files
Targeted route review
Migration safety review
Namespace/import review
Permission boundary review
Tenant-context review
Blade syntax review for changed views
Secret leakage grep
Regression note
Known limitation note
Next command
```

For data stages, also validate sync idempotency and reconciliation behavior. For write stages, also validate double-submit protection, audit atomicity, and partial-failure recovery.
